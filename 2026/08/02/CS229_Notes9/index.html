CS229 Notes 9 : LLM 基础 (2)

CS229 Notes 9: LLM 基础 (2)

这个系列是本人学习CS229的学习笔记。本文是第九篇文章，对应大语言模型系列讲座的第二讲。本讲主要涵盖注意力机制变体（GQA、滑动窗口注意力）、专家混合（MoE）架构，以及大语言模型的使用方式（上下文学习、零样本学习、指令微调）。

一、Transformer 注意力回顾与 KV Cache

注意力的核心是三个量：查询（Queries）、键（Keys）、值（Values）。对一个单头注意力来说，每个时间步都对应一个查询向量 q1,…,qTq_1,\dots,q_Tq1​,…,qT​、一个键向量 k1,…,kTk_1,\dots,k_Tk1​,…,kT​ 和一个值向量 v1,…,vTv_1,\dots,v_Tv1​,…,vT​。

注意力做的就是对这些向量取内积，再算 softmax。在自回归（Autoregressive）模型中，任何时候都不能去注意发生在"之后"的东西，只能注意过去。于是 q1q_1q1​ 只能注意 k1k_1k1​，q2q_2q2​ 可以注意 k1,k2k_1,k_2k1​,k2​，依此类推，qtq_tqt​ 可以注意 ttt 时刻之前的所有键。

用矩阵形式写，把 q1,…,qTq_1,\dots,q_Tq1​,…,qT​ 排成矩阵 QQQ，k1,…,kTk_1,\dots,k_Tk1​,…,kT​ 排成矩阵 KKK，v1,…,vTv_1,\dots,v_Tv1​,…,vT​ 排成矩阵 VVV，单头注意力的公式就是

Attention(Q,K,V)=softmax(QK⊤+MdH)V,\text{Attention}(Q,K,V)=\text{softmax}\left(\frac{QK^\top+M}{\sqrt{d_H}}\right)V, Attention(Q,K,V)=softmax(dH​​QK⊤+M​)V,

其中 MMM 是因果掩码（Causal Mask）：把那些"无效"的注意力位置（即未来位置）置为 −∞-\infty−∞，经过 softmax 后权重就变成 0，从而不会被使用；softmax 是逐行（Row-wise）的。

多头注意力（Multi-Head Attention） 就是很多个单头注意力的复制品——每个头有各自独立的 Q、K、V 投影矩阵（即"相同的架构、不同的权重"）。每个头各自独立地做内积、掩码、softmax 与加权求和，再拼接（Concatenate）起来作为这一层的输出。

  • 计算量：注意力分数矩阵是 T×TT\times TT×T 的，计算量至少是 O(T2)O(T^2)O(T2)（随序列长度二次增长）。
  • 存储（Memory）：TTT 越大，需要存进内存的东西越多——所有头的 Q,K,VQ,K,VQ,K,V 都要占内存。

不过有一点可以优化：其实不需要把 QQQ 全部存下来。在自回归生成过程中，随着时间步推进，之前算过的查询已经用过、可以丢弃，真正需要的只有"最后一步"的那个查询。相反，KKK 和 VVV 是后面每一步生成都要反复用到的，所以全部历史键值都必须留在内存里。也就是说，K,VK,VK,V 的存储是随 TTT 线性增长的——这正是所谓的 KV Cache（键值缓存）：推理时必须把每个头的所有 KKK 和 VVV 都存在 GPU 显存里。

KV cache 的存储量非常可观，从系统角度看这会带来严重的限制：

  • 显存被大量占用，导致批处理（Batch）里能容纳的序列数量非常有限。
  • Batch size 上不去，就无法在多个样本之间获得足够的并行度来利用 GPU 的全部算力。
  • 推理时模型是内存受限（Memory-Bound） 的——GPU 空有一身算力，却因为等内存而闲着，计算侧始终吃不饱。
  • 用 MFU（Model FLOPs Utilization，模型利用率） 来衡量吞吐，此时 GPU 是在"等喂数据"。

正是因为这个瓶颈，人们意识到减少需要缓存的 KV cache 量非常有价值——这正是下一节分组查询注意力（GQA）的动机。

二、分组查询注意力（GQA）

标准的注意力里，每个头都有自己独立的键和值。分组查询注意力（Grouped Query Attention，GQA） 的做法是：减少键（以及值）的数量，但保持查询的数量不变——让多个查询头共享同一组键和值。

这里的压缩不是发生在时间维上，而是发生在"头"（Key/Query Dimension）这个维度上。

设查询方面有 NHN_HNH​ 组查询序列

q1,1,…,qT,1,q1,2,…,qT,2,…,q1,NH,…,qT,NH,q_{1,1},\dots,q_{T,1},\quad q_{1,2},\dots,q_{T,2},\quad\dots,\quad q_{1,N_H},\dots,q_{T,N_H}, q1,1​,…,qT,1​,q1,2​,…,qT,2​,…,q1,NH​​,…,qT,NH​​,

其中第一个下标是时间，第二个下标是"第几组查询"（即第几个头）。键方面，组的数量要少得多：设共有 NGN_GNG​ 组键序列（以及同样数量的值序列）

k1,1,…,kT,1,…,k1,NG,…,kT,NG,v1,1,…,vT,1,…,v1,NG,…,vT,NG,k_{1,1},\dots,k_{T,1},\quad\dots,\quad k_{1,N_G},\dots,k_{T,N_G}, \qquad v_{1,1},\dots,v_{T,1},\quad\dots,\quad v_{1,N_G},\dots,v_{T,N_G}, k1,1​,…,kT,1​,…,k1,NG​​,…,kT,NG​​,v1,1​,…,vT,1​,…,v1,NG​​,…,vT,NG​​,

并且 NH>NGN_H > N_GNH​>NG​。通常还会要求 NGN_GNG​ 整除 NHN_HNH​，这样每组键值能均匀地对应若干组查询。设比例

τ=NHNG,\tau=\frac{N_H}{N_G}, τ=NG​NH​​,

那么每 τ\tauτ 组查询共享同一组键值。第 jjj 组查询所对应的键值组下标为

gj=⌊j−1τ⌋+1,g_j=\left\lfloor\frac{j-1}{\tau}\right\rfloor+1, gj​=⌊τj−1​⌋+1,

它是一个介于 111 和 NGN_GNG​ 之间的整数，表示"第 jjj 组查询属于第几组键值"。

有了映射 gjg_jgj​，第 jjj 个查询头的输出就是

Oj=softmax(QjKgj⊤+MdH)Vgj,O_j=\text{softmax}\left(\frac{Q_j K_{g_j}^\top+M}{\sqrt{d_H}}\right)V_{g_j}, Oj​=softmax(dH​​Qj​Kgj​⊤​+M​)Vgj​​,

其中 Qj=[q1,j,…,qT,j]Q_j=[q_{1,j},\dots,q_{T,j}]Qj​=[q1,j​,…,qT,j​]，Kgj,VgjK_{g_j},V_{g_j}Kgj​​,Vgj​​ 是第 gjg_jgj​ 组键值矩阵，MMM 是因果掩码。

注意：输出的头数并没有变少——仍然有 NHN_HNH​ 个头的输出，只是其中一部分输出共享同一组 K,VK,VK,V。这是 GQA 与标准多头注意力唯一的区别。

极端情形：τ=NH\tau=N_Hτ=NH​ 即 NG=1N_G=1NG​=1，只有一组键值，内存代价最小。这称为多查询注意力（Multi-Query Attention，MQA），是最早沿这条思路的方案；后来人们觉得这样太激进，于是改用更大的 NGN_GNG​。

三、滑动窗口注意力与 QK 归一化

GQA 针对的是存储问题；滑动窗口注意力针对的是计算问题。注意力分数矩阵是 T×TT\times TT×T 的，计算量是 O(T2)O(T^2)O(T2)——当序列长度 TTT 很大时，这个二次复杂度会带来真正的麻烦。必须想办法摆脱这种二次依赖。

做法是引入一个滑动窗口（Sliding Window）：设窗口大小为 WWW，让每个查询只注意最近 WWW 个位置。具体来说，qTq_TqT​ 只注意最后 WWW 个键；qT−1q_{T-1}qT−1​ 同样注意它前面最近的 WWW 个键；窗口随查询位置滑动。

用记号写，对每个查询 qtq_tqt​，注意力只作用在键的子集 kt−W,…,ktk_{t-W},\dots,k_tkt−W​,…,kt​ 上：

Ot=softmax(QtK[t−W:t]⊤dH)V[t−W:t].O_t=\text{softmax}\left(\frac{Q_t K_{[t-W:t]}^\top}{\sqrt{d_H}}\right)V_{[t-W:t]}. Ot​=softmax(dH​​Qt​K[t−W:t]⊤​​)V[t−W:t]​.

于是注意力矩阵不再是 T×TT\times TT×T，而是 T×WT\times WT×W：每个查询只需与 WWW 个键做内积。计算量从 O(T2)O(T^2)O(T2) 降到 O(TW)O(TW)O(TW)，即随 TTT 线性增长——窗口大小 WWW 通常远小于 TTT，可以看作一个常数。

这个方案的限制很明显：每个位置的注意力只覆盖很"近"的一段历史。不过，“最近 WWW 个位置"并不等于"只包含最后 WWW 个 token 的信息”——因为键本身是深层网络算出来的。设有 LLL 层，理论上每个位置最远能"看到"大约

L⋅WL\cdot W L⋅W

个 token：层数越多、回看能力越强。超过这个范围后，模型对更早的 token 就没有任何依赖了——长上下文中更早的部分会被"遗忘"。

因此，只靠滑动窗口是不行的，它会在长上下文上出问题。学界有很多论文讨论如何设计不遗忘过去的稀疏注意力（Sparse Attention）变体，但目前还没有公认的最优方案。

回顾之前对 dH\sqrt{d_H}dH​​ 的启发式论证：它假设向量各分量都处于 O(±1)\mathcal{O}(\pm 1)O(±1) 量级。但经过训练后，这个假设并不总是成立——有时查询和键的尺度会被训练推得更大或更小。

一种做法是：在取内积之前先把 Q 和 K 归一化。不再是

qj⊤kgjC,\frac{q_j^\top k_{g_j}}{C}, Cqj⊤​kgj​​​,

而是先对两边做归一化：

RMSNorm(qj)⊤RMSNorm(kgj)C,\frac{\text{RMSNorm}(q_j)^\top\text{RMSNorm}(k_{g_j})}{C}, CRMSNorm(qj​)⊤RMSNorm(kgj​​)​,

其中 RMSNorm（均方根归一化）是一种常见的归一化操作。这样在进入内积之前，向量已经被拉回差不多的尺度，绝大多数情况下分数都能保持在稳定量级。这同样是一个启发式做法，但不少开源模型确实在用。

四、专家混合（MoE）

Transformer 实际上是注意力与若干 MLP（即 FFN，前馈网络）的组合：先经过独立的（Per-Position）MLP，再做注意力，如此交替堆叠。

MLP 本质上就是一个矩阵乘法：输入向量 vvv 乘一个 D×DD\times DD×D 的大矩阵，输出向量 ooo。如果只靠"把矩阵放大"来扩展模型，代价是二次方的：把 D×DD\times DD×D 翻倍，计算量变为原来的 4 倍、内存变为 2 倍。

专家混合（Mixture of Experts，MoE） 的想法是：与其计算一个巨大无比的矩阵，不如把计算"并行化"地拆开。

不再让 vvv 乘以一个大矩阵，而是准备一大堆所谓的"专家"（Expert）E1,E2,…,EKE_1,E_2,\dots,E_KE1​,E2​,…,EK​，每个专家 EiE_iEi​ 都是一个（较小的）MLP 子网络。输入 vvv 先经过一个路由（Routing） 模块，决定把它送到哪些专家，最后把选中专家的输出做一个聚合（加权平均），得到最终输出。

关键之处在于：并不是每个 token 都会用到全部专家——对不同输入、不同 token，路由会选择不同的专家子集。

MoE 的核心收益是：把"内存/参数量"和"计算量"解耦。模型可以有大量的参数（因为专家 EiE_iEi​ 很多），但每次实际参与计算（被激活）的专家数很少。例如：

总专家数 M=128,每次激活的专家数 K=8.\text{总专家数 } M=128,\qquad \text{每次激活的专家数 } K=8. 总专家数 M=128,每次激活的专家数 K=8.

也就是说，128 个专家都常驻在内存里，但每次推理只动用其中 8 个。这样可以在不显著增加计算量的情况下不断加专家、加参数。这也解释了为什么如今读大型开源模型的规格时，人们不说"70B 模型"，而说"30B A3B"（总参数 30B、激活 3B）：把所有专家参数加起来共有 30B 总参数，而真正做推理时只有 3B 参数被激活。

MoE 最初的非系统视角动机是：人们相信这些专家各自承担不同的专业化（Specialization） 角色——比如专家 1 擅长数学、专家 2 擅长物理、专家 3 擅长通用英语、专家 4 擅长编程。

路由是按每个 token、每一层决定的——每一层都有大量并行的 MLP，每个位置的 MLP 都要单独决定用哪个专家，下一层还要再决定一次。所以专业化既针对位置也针对层。

路由不是按"序列"决定的，而是按每个 token、每一层独立决定的。

路由本身也是学出来的，由一个通常较小的路由模块完成。一种典型设计如下：

设输入是某个隐藏向量 hth_tht​，路由模块先做一次投影加激活：

r=σ(ht⊤Wr)∈RM,r=\sigma\left(h_t^\top W_r\right)\in\mathbb{R}^{M}, r=σ(ht⊤​Wr​)∈RM,

其中 MMM 是专家总数，σ\sigmaσ 可以是 softmax 或 sigmoid。得到的 MMM 维向量 rrr 表示各专家的相对重要度。然后选取其中最大的 KKK 个分量，构成激活集合

S=arg⁡top-K(r),S=\arg\text{top-}K(r), S=argtop-K(r),

即 SSS 是 rrr 中最大 KKK 个下标组成的集合。接着对每个 s∈Ss\in Ss∈S 运行对应的专家 EsE_sEs​，得到输出 Es(ht)E_s(h_t)Es​(ht​)，最后把这些输出做加权求和：

O=∑s∈SαsEs(ht),αs=rs∑s′∈Srs′,O=\sum_{s\in S}\alpha_s E_s(h_t), \qquad \alpha_s=\frac{r_s}{\sum_{s'\in S}r_{s'}}, O=s∈S∑​αs​Es​(ht​),αs​=∑s′∈S​rs′​rs​​,

权重 αs\alpha_sαs​ 是 rrr 在选中集合上的重新归一化（Renormalization），使得 ∑s∈Sαs=1\sum_{s\in S}\alpha_s=1∑s∈S​αs​=1。

有的设计里有所谓共享专家（Shared Expert）——在 MMM 个专家中，保留一个"永远被使用"的专家，每个位置、每一层都一定用到它，其余专家再按 top-K 方式挑选。DeepSeek V3 采用的就是这种设计，理由是共享专家承载关于语言、通用英语等的"公共知识"，每个 token 都需要；其余专家负责可移动的专业化。

训练中常常会对路由施加正则化（Regularization），希望路由的分布尽可能均匀，原因有二：

  1. 若路由总是指向某两个专家、其余专家从不被使用，那么存储其余专家的内存就白费了，模型的有效参数量并没有达到其参数规模宣称的大小。
  2. 路由不均匀还会让基础设施很难设计：若每个专家被部署在不同卡上、各卡负载差异太大，推理效率也会变差。

DeepSeek 的论文甚至提到过一种动态调度：美国白天某些专家使用频繁，就给它们多配 GPU；到了中国时段的白天，因为使用场景变化，另一些专家激活更多，于是把 GPU 调度给它们。

一个参数万亿但不是 MoE 的稠密（Dense）模型，几乎不可能在真实世界部署——服务延迟太长、成本太高。而同样是万亿参数、激活 30B 的 MoE 模型，成本大致相当于 30B 模型，却还能享受参数量增加带来的能力提升。

五、上下文学习与零样本学习

设下游任务有 nnn 个示例 (x1,y1),(x2,y2),…,(xn,yn)(x_1,y_1),(x_2,y_2),\dots,(x_n,y_n)(x1​,y1​),(x2​,y2​),…,(xn​,yn​)。上下文学习（In-Context Learning） 的做法是：把这些示例直接拼成一段 token 序列。例如写成：

这整段字符串就是发给大语言模型的输入，最后放测试输入 xtestx_{\text{test}}xtest​ 并以 “A:” 结尾，然后让模型接着生成——希望它把答案填出来。

一个直观的例子：

大多数人会猜 17：2+3=52+3=52+3=5、6+7=136+7=136+7=13，于是 15+2=1715+2=1715+2=17。这里的"学习"就在于从两个示例里学会了一个符号的含义。人能做到，模型从少量示例中也能做到同样的事。

另一个例子是邮件分类：假设想把邮件分为"账单"“技术”"会计"等类别。可以把 prompt 写成：说明要把消息分成 A、B、C 三类，然后给出示例——“消息 1 → A”“消息 2 → B”……测试时只给出新消息让它补全标签。模型能从这些示例中反推出 A 代表账单邮件、B 代表技术/客服邮件，然后给出正确标签。注意，即使故意不告诉它 A、B、C 的含义，它也能 work。

上下文学习有一个非常重要的性质：模型参数一个字都没有更新。你只是把示例当作字符串塞进上下文，模型本身没有任何改变。如果你相信"智能来自模型参数"，那么上下文学习并不会显著提升模型的基础能力——它更像是在学习风格、或者一些简单的定义。

完全没有训练，只是在提示（Prompting） 它。

当然有些难的规律也能学到一部分，但能学到多难的东西是有限的：例如给模型看医学影像判断是否癌症，光靠几个示例是不行的，还是得做某种微调。

更极端的版本是零样本学习（Zero-Shot Learning）：把示例全部删掉，只告诉模型任务是什么。可以尽可能用文字描述每个标签的含义，但一个示例都不给，只给任务描述（Task Description），然后让模型直接生成答案；有时还会指定想要的输出格式——比如 JSON 或某种结构化输出。

如今几乎没人再给模型少样本示例了（除非极特殊情况），直接零样本就好。

少样本与零样本能力是 GPT-3 论文最重要的发现之一。之所以令人震惊，是因为模型参数从未被更新——大家觉得至少得在新任务上稍微调一调模型，结果完全不用以标准方式微调，只要提示一下就行。这从根本上改变了模型在工业界落地的便捷程度。

旧时代做行业应用是这种流程：想解决某领域问题 → 从该领域收集大量数据 → 标注 → 在领域数据上训练 → 部署一个专用模型。部署流程复杂无比。

现在则完全不必：一个开箱即用（Off-the-Shelf）的模型，各家公司自己写 prompt 就行；做智能体（Agentic）任务时偶尔有一些脚手架（Scaffolding），但本质上只是非常轻量的定制——写任务描述、偶尔给几个示例。甚至可以定义复杂的工作流：把公司给新员工的入职文档直接丢给模型，模型就会照着指令办事。

六、监督微调与指令微调（SFT）

零样本与上下文学习的能力最初是"自然涌现"的。接下来人们自然想：能不能强化（Strengthen/Reinforce） 这种能力？方法其实相当简单，就是做某种形式的 SFT，业界称之为指令微调（Instruction Tuning）。

做法是：收集大量"指令—答案"对的数据集 (Xi,Yi)(X_i,Y_i)(Xi​,Yi​)，其中 XiX_iXi​ 是指令（Instruction）或任务描述（Task Description），YiY_iYi​ 是答案。然后从已有的 checkpoint 继续训练，让模型学会"照做"。

设 XiX_iXi​ 有若干 token（作为条件，视为已知，不需要预测），YiY_iYi​ 有 TiT_iTi​ 个 token。最大化"给定 XiX_iXi​ 看到 YiY_iYi​ 的概率"，即最小化负对数似然：

L(θ)=−1n∑i=1nlog⁡Pθ(Yi∣Xi).\mathcal{L}(\theta)=-\frac{1}{n}\sum_{i=1}^{n}\log P_\theta(Y_i\mid X_i). L(θ)=−n1​i=1∑n​logPθ​(Yi​∣Xi​).

由于 YiY_iYi​ 是序列，这个对数可以分解为逐步（Per-Step）的损失之和：

log⁡Pθ(Yi∣Xi)=∑t=1Tilog⁡pθ(yti∣Xi, y<ti),\log P_\theta(Y_i\mid X_i)=\sum_{t=1}^{T_i}\log p_\theta\left(y_t^i\mid X_i,\,y_{<t}^i\right), logPθ​(Yi​∣Xi​)=t=1∑Ti​​logpθ​(yti​∣Xi​,y<ti​),

其中 ytiy_t^iyti​ 是 YiY_iYi​ 的第 ttt 个 token，y<tiy_{<t}^iy<ti​ 是它之前的所有 token。于是整体目标就是

L(θ)=−1n∑i=1n∑t=1Tilog⁡pθ(yti∣Xi, y<ti),\mathcal{L}(\theta)=-\frac{1}{n}\sum_{i=1}^{n}\sum_{t=1}^{T_i}\log p_\theta\left(y_t^i\mid X_i,\,y_{<t}^i\right), L(θ)=−n1​i=1∑n​t=1∑Ti​​logpθ​(yti​∣Xi​,y<ti​),

即：给定指令 XiX_iXi​ 和前 t−1t-1t−1 个答案 token，预测第 ttt 个 token——本质上还是标准的下一 token 预测（Next-Token Prediction），只是条件里加上了指令。

任何符合这种形式的训练都叫监督微调（Supervised Fine-Tuning，SFT）：因为你在提供监督信号（那些 YYY），而且是从初始 checkpoint 出发做微调。而指令微调（Instruction Tuning）是 SFT 中数据集恰为"指令式"数据的那一类；其他场景也可以用同样形式的损失函数做 SFT，只是数据集不同（例如领域数据微调）。
